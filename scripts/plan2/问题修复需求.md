# plan2 运行与结果汇总：四项问题修复需求

> 交付对象：Qoder。本文记录对 `matmul/best-matmul/scripts/plan2/` 的代码检查结果，目标是修复结果可信度和独立运行入口的问题，并补充可离线执行的回归测试。本文不是性能测试结果；没有 H100 或 NCU 时不要编造 GPU 测试结论。

## 背景与范围

plan2 通过 `run.sh` 编译并依次执行同机 V1/V2 基准、PIPE、GMMA_N、CTA 和大 CTA 对照；`run_variants.sh` 使用 `scripts/common/runner_common.sh` 执行已有构建，`collect_results.py` 汇总各组 CSV。构建与实验结果分别位于 `best-matmul/build/plan2/` 和 `best-matmul/output/plan2/`。

请保留既有实验矩阵、同一形状/布局的基准比较、正确性验证先于一键性能测试，以及普通 CUDA Event 计时口径。不要覆盖或删除已有构建、原始结果、验证日志和其他计划的数据。若调整共享执行器，需保证 plan1 的调用方式仍然可用。可以更新 plan2 README 和测试代码，使其与最终实现一致。

以下路径均相对于 `matmul/best-matmul/`。

## 问题 1：验证未完成或失败可能被标记为 PASS（P1）

**位置：**`scripts/plan2/collect_results.py` 的 `load_validation()`、`add_meta()`；验证程序为 `tests/full_output_validation.cu`，执行器为 `scripts/common/runner_common.sh`。

**现状与复现：**汇总器只检查日志中是否包含大写 `FAIL` 或 `PASS`。验证程序首先打印 `Mapping PASS`；之后某一输出错误时，日志可能是：

```text
Mapping PASS: 128 compute threads cover ...
Full-output failure: layout=NT, input=2, ...
```

此时 `failure` 为小写，汇总器会把该日志判为 `PASS`。进程超时、被中断或异常退出时也可能只留下前面的 `PASS`。此外，找不到某配置的验证日志时，`summary_all.csv`/`runs_all.csv` 的 `validation_status` 当前为空，而不是 README 描述的 `UNKNOWN`。

一键 `run.sh` 在验证失败时会停止；问题主要影响手动分步运行、收集不完整结果或对已有结果重新汇总。

**修复要求：**

1. 不能把单个子检查或 `Mapping PASS` 视为全输出验证成功。只有能确认整个验证程序正常退出且输出完整成功标记时，才能标记 `PASS`。验证程序最终成功标记为 `All full-output regressions PASS`。
2. 捕获或保存每个验证进程的退出状态，以区分失败、超时和中断；判定失败不依赖大小写敏感的 `FAIL` 子串。历史日志如果没有足够证据证明成功，应标为 `UNKNOWN`，不能推断为通过。
3. 明确、稳定地输出 `PASS`、`FAIL`、`UNKNOWN`：缺少日志、仅有部分 `PASS` 或无法确定退出状态时为 `UNKNOWN`；有明确验证错误或非零退出状态时为 `FAIL`。即使存在最终成功标记，若进程非零退出也不得判为 `PASS`。
4. `summary_all.csv`、`runs_all.csv` 与 `validation.csv` 对同一配置的状态应一致；`validation.csv` 应能体现缺少验证记录的配置，并保留可追溯的日志/状态文件路径。不得为没有通过验证的配置制造通过状态。

**验收：**离线覆盖完整成功、`Mapping PASS` 后输出小写 `Full-output failure`、中途终止或超时、非零退出但日志含 `PASS`、只有 `Mapping PASS`、日志缺失等情况；确认两个汇总表与验证表中的状态一致。

## 问题 2：汇总使用可变 manifest，可能误标历史配置（P1）

**位置：**`scripts/plan2/collect_results.py` 的 `find_manifest()`、`load_manifest()`、`add_meta()`。

**现状与复现：**当前先读取结果目录 `build_dir.txt` 指向的构建目录中的 `manifest.tsv`；只有找不到时，才读取实验子目录保存的 manifest。假设某组运行时保存的快照中 `v2_p3` 的 `gmma_n=128`，后来构建目录对应记录变为 `gmma_n=64`，重新汇总会给旧的性能结果标上 `64`。已用临时目录和两份不同的 manifest 验证此行为。

每个 `run_variants.sh` 的结果组已经保存执行时的 `manifest.tsv`。手动分步运行还可能让不同组引用不同构建，因此不能不加核对地将某一份全局清单用于所有组。

**修复要求：**

1. 优先使用各实验组在运行时保存的 manifest 快照，为该组每一行附加 `version`、`gmma_n`、`inflight` 等配置；若提供显式 `--manifest`，应定义清楚其作用，并与组内快照核对，不能静默覆盖不同配置。
2. 对同一配置 ID 的记录检查相关配置字段。若组内快照、其他组快照、显式 manifest 或当前构建 manifest 不一致，应明确报错或在输出中作不可忽略的冲突标记；不能把不同配置的数据当成同一配置，也不能静默选择一个值。
3. 针对已搬运到其他机器的结果，允许仅凭结果目录内的 manifest 快照汇总；不能要求原服务器的 `build_dir.txt` 绝对路径仍然存在。缺失清单时，不得猜测配置，应明确标记未知或报错。
4. 验证状态与实验组配置的对应关系也要可追溯：如果验证与某实验组使用不同构建，不能仅根据相同 ID 就把另一个构建的验证状态标为通过。

**验收：**构造运行时快照为 `GMMA_N=128`、当前构建清单为 `64` 的结果；不得将历史结果静默标成 `64`。覆盖组间配置冲突、显式 manifest 冲突、原构建路径不可访问、组内清单缺失以及相同 ID 对应不同构建的情况。原始实验组 CSV 和 manifest 不得被修改。

## 问题 3：默认汇总可能静默选择未完成的实验（P2）

**位置：**`scripts/plan2/collect_results.py` 的 `find_result_dir()` 与汇总入口。

**现状：**默认选择 `output/plan2/` 下含任意一份子目录 `summary.csv` 的目录，按照 summary 文件修改时间排序；不检查 `status.txt` 或五个实验组是否完整。如果脚本执行到一半失败，前面已生成的组仍会满足选择条件，汇总器不会明显提示失败或缺失组。旧 summary 被重新写入或复制后，文件修改时间也可能使旧运行被误选为“最新”。

当前一键实验预期的组是 `00_baseline`、`01_pipe`、`02_gmma`、`03_cta`、`04_large_cta`；但显式传入的目录也可能是用户有意只运行一部分的结果，不应一概视为错误。

**修复要求：**

1. 定义并记录默认自动选择的规则，不能仅凭某份 summary 的修改时间声称选择了最新完整实验。优先选择可确定已完成的运行，并考虑 `status.txt` 与预期实验组；不能误把 `--build-only` 的 `COMPLETE` 当成 benchmark 已完成。
2. 对失败、运行中、中断、缺少状态文件或缺少实验组的结果，明确显示运行状态和缺失组；如允许显式汇总部分结果，应醒目标记为部分结果，而非伪装成完整结果。
3. 不要跨运行目录混合数据，不要修改或删除历史原始结果。明确默认没有完整运行时的行为，并与 README 一致。

**验收：**使用临时结果目录覆盖完整运行、`FAILED stage=...`、`RUNNING`、状态缺失、`--build-only`、只含部分组，以及旧运行的 summary 修改时间晚于新运行的情况。验证自动选择和显式指定部分结果时的提示、退出状态与文档一致。

## 问题 4：独立运行入口的默认构建目录与编译入口不一致（P2）

**位置：**`scripts/plan2/run_variants.sh` 的 `default_build_dir`；`scripts/plan2/run.sh` 的 `--build-only` 默认路径。

**现状与复现：**`run_variants.sh` 默认查找 `build/plan2/h100_pcie/manifest.tsv`，而 `bash scripts/plan2/run.sh --build-only` 默认创建 `build/plan2/<时间戳>_<进程号>/`。因此执行提示中的编译命令后，如果再次直接运行 `run_variants.sh` 而未指定 `--build-dir`，仍会提示找不到 manifest。README 当前的分步示例显式传入 `--build-dir`，该示例不受影响。

**修复要求：**

1. 明确选择一种可靠的交互：要求显式指定 `--build-dir` 并给出可复制的路径获取方式，或提供可追溯且不会误选旧构建的默认路径解析机制。不得静默选择其他实验的构建，也不得覆盖已有构建。
2. 错误提示、`--help`、`--dry-run` 和 README 必须符合实际行为。编译结果仍应按计划分类存放在 `best-matmul/build/plan2/`，实验结果继续存放在 `output/plan2/`。
3. 保持 plan2 不调用 plan1 专属脚本；两者可以共享 `scripts/common/runner_common.sh`。避免破坏 plan1 现有默认值和参数行为。

**验收：**在临时目录中以模拟工具运行一次 `--build-only`，再按文档和错误提示执行分步验证/benchmark 或其 dry-run；确认引用的确是该次构建，而不是固定的错误目录或上一次的构建。覆盖无构建目录、目录不存在及多个历史构建的情形。
