# 00 · 测试环境与分析说明

> 本页是整个 `ncu报告分析` 系列的基线页。所有后续 V1–V5 单内核笔记、横向对比、优化方案和实验计划，均以本页定义的环境、报告映射、指标口径和可比性边界为准。
>
> 分析对象：`matmul/best-matmul` 中 5 个 Hopper FP16 GEMM kernel（V1–V5），报告目录为 `reports/h100_pcie/manual_20261020_020722_2403487/`。

---

## 1. 分析目标与边界

本系列回答四个问题：

1. 每个 kernel 的时间花在哪里？是 Tensor Core 算得慢，还是数据没送到、同步没排开、写回拖尾？
2. 每个结论对应哪条 NCU 指标、哪条 SASS/PTX、哪一行源码？
3. 版本之间的性能变化由哪些源码改动造成？哪些是因果，哪些只是相关？
4. 下一步应该改什么、怎么验证、预期收益多大、风险是什么？

**不做的事**：不在分析完成前重写 kernel；不把“Warp Specialization / 更多 stage / 更高 occupancy”当作默认正确；不把 warp stall 采样占比直接当作 kernel 时间占比。

## 4. 测量方法与两种时间口径

### 4.1 Benchmark 计时（用于 TFLOPS 排名）

- CUDA Event 批内平均，20 launches/batch，100 batches，≥300 次 warmup；
- 每进程取 p50，跨 5 个进程取中位数；
- `TFLOPS = 2MNK / (median_p50_ms × 1e9)`；
- 基准固定 alpha=1、beta=0、FP16 in/accum/out、dense、无 epilogue fusion。
- 运行前有 telemetry（功率/时钟/温度），运行时有外部进程干扰时标记 `flagged_runs`。

> 计时结果见 `bench_core/summary.csv`。**PIPE/M256 的 4096³ 基准受到外部进程污染，绝对 TFLOPS 不可用**；K=256 的 PIPE 结果干净，保留使用（详见 [06 · 横向对比](06-五个Kernel横向对比分析.md) 第 6 节）。

### 4.2 NCU 计时（用于瓶颈定位）

- `ncu --set focused --cache-control all --clock-control none --launch-skip 50 --launch-count 1`；
- Kernel replay，23 passes；冷缓存；
- NCU 的 `gpu__time_duration.sum` 是单次 replay 的 kernel 时间，**含冷启动/队列空窗**，与 benchmark 的稳态批平均不可直接相减；
- 报告默认 shape 4096×4096×4096 与 4096×4096×256；M/N/K 全整除，无边界分支。

**结论**：
- 排名与百分比变化用 benchmark；
- 瓶颈归因用 NCU 指标与 SASS；
- 两者只做方向一致性校验，不做数值互换。

## 5. 指标口径与阅读注意事项

| 系列 | 指标 | 含义 | 本系列用法 |
|---|---|---|---|
| 算力 | `sm__pipe_tensor_cycles_active.avg.pct_of_peak_sustained_active` | Tensor pipe 活跃周期 / 峰值 | 主算力指标；70%+ 表示接近此 kernel 形态的上限 |
| 综合 | `gpu__compute_memory_throughput.avg.pct_of_peak_sustained_elapsed` | SM/内存各管线最大吞吐 | 只用于判断“是否整体饱和”，不单独归因 |
| 显存 | `gpu__dram_throughput.avg.pct_of_peak_sustained_elapsed` | DRAM 带宽利用率 | <50% 时通常不是 DRAM 带宽瓶颈 |
| L2 | `lts__throughput.avg.pct_of_peak_sustained_elapsed` | L2 吞吐利用率 | 与 DRAM、L1TEX 交叉判断 |
| L2 命中 | `lts__t_sector_hit_rate.pct` | L2 sector 命中率 | 解释 DRAM 与 L2 的差值 |
| TMA | `sm__pipe_tma_cycles_active.avg.pct_of_peak_sustained_active` | TMA 指令管线活跃 | **测的是指令发射占用，不是 TMA 数据引擎带宽**；低值不等于 TMA 不是瓶颈 |
| TMA 请求 | `l1tex__tmain_requests.sum.pct_of_peak_sustained_elapsed` | TMA 请求占 L1TEX 峰值 | NT/TN 请求粒度差异的直接证据 |
| TMA 数据路径 | `l1tex__m_xbar2l1tex_read_sectors.sum.pct_of_peak_sustained_elapsed` | L1TEX 读 crossbar sector 率 | 与 DRAM% 一起判断是否数据路径饱和 |
| 调度 | `smsp__warps_eligible.avg.per_cycle_active` | 每周期可发射 warp 数 | <0.5 说明调度器经常无 warp 可发 |
| 发射 | `smsp__issue_active.avg.pct_of_peak_sustained_active` | 发射槽利用率 | 与 eligible 一起看；低 eligible + 低 issue = 真等待 |
| 指令间隔 | `smsp__average_warps_active_per_inst_executed.ratio` | 每条已执行指令的平均活跃 warp 数（WCPI） | 越高说明指令间等待越长；受 warp 数影响，跨版本需谨慎 |
| Stall | `smsp__average_warps_issue_stalled_<reason>_per_issue_active.ratio` | 每个 issue-active 周期里，因该原因停滞的 warp 数 | 用于排序 stall 原因；不是时间占比 |
| 占用 | `sm__warps_active.avg.pct_of_peak_sustained_active` | Achieved Occupancy | 受 SMEM/寄存器/线程数共同限制 |
| 资源 | `launch__registers_per_thread` / `launch__shared_mem_per_block_dynamic` | 寄存器/动态 SMEM | 判断 occupancy 限制来源 |
| 写回 | `memory_l2_theoretical_sectors_global` / `_ideal` / `_excessive` | 全局写 L2 理论 sector / 理想 / 超额 | 证明 V1/V2 的 16-bit 写回是否 2× sector |

### 5.1 四条硬性解读规则

1. **Warp stall 采样百分比 ≠ kernel 时间百分比**。它是“采样到某 warp 停在该 PC/原因”的分布，受活跃 warp 数、PC 合并、采样粒度影响。V4/V5 的采样占比被 8 个 warp（含 4 个空转 producer warp）放大，不能直接与 V2/V3 的 4 warp 比。
2. **`WARPGROUP.DEPBAR.LE` 是 WGMMA 异步完成等待**，不是“barrier 指令太多”。它出现多，说明代码在等 GMMA 批次完成（数据依赖），不能靠删指令解决。
3. **`SYNCS.PHASECHK.*.TRYWAIT` + `NANOSLEEP` 是 mbarrier 自旋**。它高说明在等 TMA 到达或等消费者释放槽位；要区分“消费者等数据”还是“生产者等空间”，必须看 PC 对应的是 full 还是 empty barrier（本系列按 SMEM offset 与源码行区分）。
4. **NCU 的 Tensor% 与 benchmark 的峰值占比不是同一分母**。同一份 V1-NT：NCU Tensor 66.23%，而 benchmark 420.2/756.5 = 55.6%；差异来自时钟控制与峰值定义。两者只能各自纵向比较，不能把 NCU 的 100% 当作 756.5 TFLOPS 去换算。

### 5.2 不做的推断

- 不因 barrier stall 高就断言“同步写错”；
- 不因 occupancy 高就断言“更快”；
- 不因使用 WS 就断言“TMA/计算重叠”；
- 不因 `Excessive Sectors` 高就断言“C 写回是瓶颈”；
- 不因 TMA pipe 活跃低就断言“TMA 不是瓶颈”（该指标只测指令发射）。

## 6. 可比性分级

| 级别 | 数据 | 用途 |
|---|---|---|
| **A. 可直接比较** | 同一 shape、同一 layout、同一 CTA tile、同一 PIPE、同一 GMMA_N、同一 EPILOGUE 配置下的 V1–V5；K=256 的 PIPE=2/3/4（干净基准） | TFLOPS 排名、版本 delta、Tensor/DRAM/L2/occupancy 对照 |
| **B. 仅定性参考** | NCU 单次 replay 的 duration 与 benchmark 时间；4096³ 的 PIPE/M256 基准（受外部进程污染）；8192³（不稳定，flagged）；K=256 的 L2/DRAM 百分比（受冷缓存与短 kernel 影响） | 趋势、机制解释，不作绝对排名 |
| **C. 需重测** | 4096³ PIPE=2/4、M256 的绝对 TFLOPS；V5 warm-cache 全量；缺少 L1 命中的 V3+；无 per-warp stall 归因的 producer/consumer 拆分 | 优化决策前的复现实验 |

**测量污染记录**：PIPE/M256 的 4096³ benchmark 运行时，外部 `./test` 进程占用约 450 MiB，使 medians 膨胀约 1.81–2.0×（V3 0.52099 vs core 0.28736 ms；V4 0.749218 vs 0.373979；V5 0.750639 vs 0.377526）。**该批 4096³ 绝对 TFLOPS 全部弃用**；K=256 同批数据干净（短 kernel，外部进程影响可忽略），保留。

## 7. 数据缺失与已知限制

| 缺失项 | 影响 | 处理 |
|---|---|---|
| TMA 数据引擎延迟/队列深度计数器 | 无法直接把 V4/V5 NT 的消费者饥饿归因到“请求率”还是“延迟” | 用请求数、TMA 指令率、生产者/消费者等待位置做排除法，并列入 [09](09-后续实验与NCU验证计划.md) |
| V3+ 的 L1 命中率 | 无法评估 L1 tag/data 路径 | 标 N/A，不编造 |
| Warm-cache NCU | 只代表冷缓存稳态 | 结论限定为冷缓存；benchmark 为重复同数据，L2 可能更热 |
| 固定时钟 NCU | Tensor% 受运行期时钟影响 | 只用同一批报告内相对比较 |
| Per-warp/Per-PC 的 producer vs consumer 分离 | V4/V5 的 stall 采样混合了空转 producer warp | 用 SASS PC 与 barrier offset 归类，不完全依赖采样百分比 |
| 4096³ PIPE/M256 干净基准 | 无法判断深流水在长 K 下的收益 | 列入 [09](09-后续实验与NCU验证计划.md) 重测 |
| 8192³ 稳定性 | V1 TN、V5 NT 异常低 | 仅作定性，不参与排名 |
| Benchmark 期间功耗/时钟遥测 | 无法排除功耗降频对长 kernel 的影响 | 记录 350 W cap；建议后续以 telemetry 同步 |

## 9. 报告与源码引用约定

- 指标引用格式：`指标名 = 值（单位）`，并注明 `4096³ / NT / V4` 这类上下文；
- SASS 引用格式：`opcode @ 0x地址`，地址来自 `ncu --import ... --page source --csv` 或 `disasm/`；
- 源码引用格式：`文件:行号`，例如 `kernels/detail/tma_wgmma_device.cuh:167`；
- 证据等级：**已证实**（指标 + SASS/源码 + 机制闭环）、**较高可能性**（多条证据一致但缺直接计数器）、**待验证假设**（需实验）；
- 所有百分比变化定义为 `(new/old − 1) × 100%`，与 benchmark 表一致。
