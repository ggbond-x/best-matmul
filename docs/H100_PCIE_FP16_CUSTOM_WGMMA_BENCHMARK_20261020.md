**一句话结论**：15 个配置、6 个形状 × NT/TN、600 个全输出用例全部 PASS；正式成绩最高 **482.4 TFLOPS**（v4、4096³、TN、284.89 µs），为 H100 PCIe dense FP16 峰值 756.5 TFLOPS 的 **63.8%**。v2 的双批在途是唯一稳定收益（几何平均 1.118×）；v3 基本持平；v4 只在 1024³/K=256 的 TN 上明显获益（+5.4%/+8.0%），却让 NT 主要形状损失 22–38% 吞吐，v5 相对 v4 无增量；PIPE=2 只对 v3 有意义，PIPE=4 全面退化。

## 1. 结论摘要

- **最高成绩**：v4 / 4096×4096×4096 / TN = **284.89 µs、482.4 TFLOPS（63.8% 峰值）**；v2 / 4096³ / NT = 480.0 TFLOPS；v3 / 1024×16384×4096 / TN = 469.2 TFLOPS。
- **v2 最值得保留**：相对 v1 的 12 项速度比几何平均 **1.1178×**，11/12 胜，范围 0.9812–1.3123；排除不稳定的 8192³ 后仍为 1.1058×，9/10 胜。
- **v3 的合并写回总体持平**：相对 v2 几何平均 **1.0028×**，8/12 胜，范围 0.9628–1.0291；所有变化都在 ±3% 内。
- **v4/v5 不是普适加速**：v4/v3 几何平均 **0.9149×**（5/12 胜），v5/v4 **0.9940×**（3/12 胜）。v4 只在 1024³ TN（+5.4%）和 K=256 TN（+8.0%）明显快于 v3，4096³ TN 仅 +0.5%；v5 相对 v4 反而略降。代价是 NT 主要形状吞吐损失 22–38%（1024³ −38%、4096³ −23%、1024×16384 −22%），延迟分别增加 62%/30%/29%。
- **PIPE 结论**：v3 在 TN 长 K 上 PIPE=2 比 PIPE=3 快 6.7%，在 K=256 上快 11.4–13.7%，NT 长 K 持平；v4/v5 的 PIPE=2/4 都更慢，**PIPE=4 在所有版本、所有扫描问题上都退化**。
- **M256 不是 M128 的升级**：4096³ 上 NT 比 M128 慢 1.44–1.52×，TN 慢 1.06–1.12×；K=256 上 NT 慢 1.29–1.35×，TN 慢 1.09–1.15×（NCU）。原因是一个 CTA/SM、每 CTA 输出翻倍，增加计算 warpgroup 只能带来 ≤5% 的局部差异。
- **机制主线**：4096³ 的所有 PIPE=3 配置搬运的 DRAM 字节几乎相同（约 247 MB），NT 与 TN 的差别不是流量，而是**能取到的带宽**：v4 NT 659 GB/s vs TN 911 GB/s；v5 NT 647 vs TN 914 GB/s。NT 的 Tensor 利用率在 M128 上只有 51–52%、TN 为 78–79%（M256 NT 进一步降到 38%），且增加 occupancy/warp 数不能修复。
- **唯一能改变流量等级的是 v3 PIPE=2**：DRAM 流量 170.7 MB（比 PIPE=3 少 31%），L2 命中率 83–84%，驻留 3 CTA/SM；PIPE=4 则涨到 380–389 MB，L2 命中率降到 62–65%。
- **数据可用性有限制**：核心 300 个进程在干净环境完成；PIPE 与 M256 阶段的 4096³ 长 K 受到同卡外部进程 `./test`（450 MiB）干扰，官方耗时膨胀约 1.85–2.0×，只能做组内排序或使用 NCU 的相对结果；K=256 不受影响。8192³ 有 28 个 warning，排名不可靠。
- **缺口**：Compute Sanitizer 未执行（计划 18 项，实际 0）；NSYS 未执行；warm full NCU 失败且没有 `.ncu-rep`。因此“无内存/同步错误”和 warm-cache 下的完整指标仍未闭环。

### 2.3 正式成绩口径

- 一个样本 = 一个批次的总 Event 时间 / 该批启动次数；每批 20 次 launch，100 批，预热不少于 300 次 launch。
- 每进程取批均延迟的 p50；跨进程取各进程 p50 的**中位数**。`TFLOPS = 2MNK / (median_p50_ms × 1e9)`。
- 速度比 >1 表示当前配置更快；`flagged_runs` 表示带 warning 的进程数，不是失败数，也没有自动剔除。
- 实际重复数：核心 **5**（计划建议 5 的倍数）、PIPE **3**、M256 **4**。版本执行顺序做了轮换。
- **NCU 日志中的时长和 TFLOPS 不是正式成绩**，只用于机制分析和相对排序。

## 4. 数据质量：哪些数字能用，哪些不能用

### 4.1 核心阶段是干净的

`bench_core` 的 300 个进程没有任何外部进程快照；遥测为 1755 MHz、约 85–300 W、47–90 °C，无功率或温度降频证据。因此核心 12 组延迟和吞吐可以作为本实验的主结果。

但核心内部仍有波动：

- **8192³ 不稳定**：28 个 warning 全部集中在 8192³，各配置 p50 跨进程差异可达 4.6–27.7%。v1 TN 的 5 个进程为 3196.5–4290.5 µs，跨度 27.66%，它的 278.0 TFLOPS 是样本分布造成的低值，不能当作 v1 的真实水平。8192³ 只用于方向性判断。
- **16384×1024×4096 NT 有系统性漂移**：v1 的漂移为 −14.7% 到 −16.6%（进程内先慢后快），v4/v5 为 +6.1% 到 +7.4%（先快后慢），15 个进程被标记。但各进程 p50 的范围很小（如 v1 472.8–483.9 µs、v4 432.3–434.9 µs），中位数仍然可用；只是 ±5% 的漂移说明热/时钟状态没有完全稳定。
- 1024³ 与 4096³ 没有 warning；K=256 只有 1 个、1024×16384 有 6 个 warning，进程间范围仍在 1–3% 左右。

### 4.2 PIPE 与 M256 阶段的 4096³ 被外部进程污染

从 PIPE 扫描开始，同卡出现一个不属于本实验的外部进程 **`./test`（450 MiB）**：PIPE 阶段 PID 3138863，M256 阶段 PID 3188132。日志中的进程快照能与耗时变化精确对齐：

- **PIPE 阶段**：全部 108 个进程快照都有该外部进程；同一份 v3 4096³ NT 从 core 的 287.36 µs 变为 520.99 µs，v4 TN 从 284.89 µs 变为 513.68 µs，膨胀约 1.8–2.0×。
- **唯一边界样本**：v3_p2 4096³ NT 的 r1（02:34:13）为 282.345 µs，r2/r3（02:34:25 之后）为 516.554/516.878 µs。外部进程在快照里从 r1 就存在，但 r1 尚未受到影响，说明它是中途开始占用资源的；这一“阶跃”不是测量噪声。
- **M256 阶段**：02:38:12 之前启动的 4096³ NT 进程都没有该进程，耗时 549.9–569.1 µs，与 NCU 的 549.6–569.1 µs 一致；之后启动的 4096³ TN 进程全部带该进程，耗时 532.6–543.4 µs，而 NCU 为 287.2–300.9 µs，膨胀 1.85×。唯一一个在该时刻之后启动的 NT 进程（`v5_m256_t256` NT r4）也变成 **1174.04 µs（2.11×）**；它被 4 个进程的中位数排除，所以 NT 汇总仍可用。
- **K=256 不受影响**：PIPE 阶段的 K=256 官方值为 39.8–71.8 µs；PIPE=2/3 的 39.8–53.2 µs 与未受干扰的 core（42.3–48.7 µs）和 NCU（40.6–49.1 µs）同量级，PIPE=4 的 51.2–71.8 µs 则是配置本身的退化。M256 的 K=256 也与 NCU 相差 2–5%。
- **时钟/功耗不是原因**：所有进程的遥测都是 1755 MHz，功率约 250–300 W，低于 350 W 上限，没有降频记录。
- **更像 HBM 带宽争用，而不是 SM 时间片轮转**：时间片轮转会同时拖慢 K=256 和 K=4096；实际只有长 K（DRAM 流量约 247 MB）变慢，而 K=256（L2 命中率 93–98%、DRAM 约 26 MB）不受影响。日志只能证明相关性，无法证明 `./test` 具体在执行什么。

### 4.4 warm full NCU 失败

`ncu_v5_4096x4096x4096_NT_warm.log` 在 application replay pass 17 得到 p50 0.393008 ms、`TFLOPS_p50=349.71`（非正式成绩），随后出现：

```text
cudaGetDevice(&device): cudaErrorUnknown: unknown error
==ERROR== Unexpected number of profiled kernels. Application replay requires that the
execution, combined with selected filters, guarantees a consistent set of kernels in all passes.
```

这说明应用重放各 pass 的 kernel 集合不一致，不能用于“warm 缓存”对比。该阶段没有生成 `.ncu-rep`，只有日志。`status.txt` 因此为 FAILED。

- v2/v3 把大形状的 NT/TN 比拉到 **0.98–1.01**，这是它们最实质的改进：布局不再决定性能。
- v4/v5 重新引入 **1.31–1.33** 的 NT 惩罚（4096³、1024×16384），但在 16384×1024 上只有 1.05。说明 producer warpgroup 的问题不是“所有 NT 都慢”，而是与 N 的大小/B 侧访问模式相关。
- 1024³ 的 2.05 是网格太小（8×8=64 CTA，少于 114 SM）叠加 producer/consumer 串行化的结果：每 SM 最多一个 CTA，没有第二个 CTA 来隐藏交接延迟。

### 5.5 形状效应

- **1024³**：只有 64 个 CTA，0.56 个波次，SM 利用率不足。v1–v3 为 14.3–18.4 µs，v4/v5 NT 增加 62% 到 23.1 µs；TN 仍为 11.3 µs。小形状应优先减少固定开销和网格量化，而不是加深流水。
- **4096³**：v2/v3 的 NT 为 286–287 µs（478–480 TFLOPS），TN 为 286.3–292.0 µs；v4 TN 以 284.89 µs 取最高分（对 v3 仅 +0.5%），但 NT 跌到 374–378 µs。它是本次机制分析的主形状。
- **8192³**：最好的是 v3 NT 429.9 TFLOPS 和 v5 TN 383.4 TFLOPS，但分别有 1 和 5 个 warning，v1 TN 的 278.0 是 27.7% 跨度的伪低值。不要把 8192³ 的版本排序当作结论。
- **K=256**：所有配置只有 176–203 TFLOPS，约 4096³ 的 40%。四个 K tile 的主循环太短，流水填充/排空和 128×128 输出写回占主导。v2 NT 191.3 和 v4 TN 203.3 是各自最佳。
- **16384×1024 vs 1024×16384**：两者 FLOPs 相同（均为 1024 个 CTA），但后者在 v1–v3 和 v4/v5 的 TN 上快 **1.34–1.43×**（如 v3 TN 417.6 → 292.9 µs，v3 NT 414.8 → 295.0 µs）；v4/v5 的 NT 因自身退化只快 1.13–1.14×。这与 CTA 光栅化顺序和 L2 复用有关：长 N 形状让连续 CTA 共享同一个 A tile，长 M 形状则要流式读取更大的 A；但本次没有对这两个形状做 NCU，只能作为待验证假设。
- **最佳配置因形状而异**：没有一个版本通吃。NT 侧 v2/v3 胜出（1024³ v3、4096³ v2、K256 v2、16384×1024 v3、1024×16384 v3）；TN 侧 1024³ 由 v5 领先（190.3 TFLOPS），4096³/K256/1024×16384 由 v4/v5 领先（其中 4096³ 对 v3 仅 +0.5%），16384×1024 反而是 v1。

### 5.6 与同页 cuBLAS 记录的参考对照

同页 cuBLAS 记录（row-major NN、默认启发式、10 次/批 × 50 样本、均值口径）与本实验的布局和统计口径不同，只能作为量级参考：

| 形状 | 自定义最佳（TFLOPS） | cuBLAS 记录（TFLOPS） | 差值 |
|---|---:|---:|---:|
| 1024³ | 190.3（v5 TN） | 227.4 | −16.3% |
| 4096³ | 482.4（v4 TN） | 409.9 | +17.7% |
| 8192³ | 429.9（v3 NT，不稳定） | 409.1 | +5.1% |
| 4096×4096×256 | 203.3（v4 TN） | 292.2 | −30.4% |

大形状的持续吞吐已经超过 cuBLAS 默认路径，但小形状和短 K 明显落后；后者更像启动/写回开销问题，而不是 Tensor Core 算力问题。

## 6. PIPE 扫描

### 6.1 NCU 主证据（4096³）

NCU cold 时长单位 µs，括号内为该配置的实测 SM 频率；`p2/p3` 和 `p4/p3` 是**按时钟归一化的相对吞吐**（>1 表示比 PIPE=3 快）。

| 版本 | 布局 | PIPE=2 | PIPE=3 | PIPE=4 | p2/p3 | p4/p3 | DRAM MB（p2 / p3 / p4） |
|---|---|---:|---:|---:|---:|---:|---|
| v3 | NT | 270.5 | 270.9 | 357.9 | **1.001** | 0.767 | 170.7 / 246.5 / 386.5 |
| v3 | TN | 256.5 | 275.5 | 320.2 | **1.067** | 0.860 | 170.7 / 247.5 / 387.4 |
| v4 | NT | 558.4 | 375.6 | 724.2 | 0.647 | 0.512 | 247.8 / 247.4 / 379.6 |
| v4 | TN | 365.9 | 271.3 | 314.3 | 0.761 | 0.874 | 247.4 / 247.1 / 386.6 |
| v5 | NT | 571.5 | 382.9 | 692.0 | 0.640 | 0.557 | 247.6 / 247.9 / 380.0 |
| v5 | TN | 367.8 | 269.3 | 316.0 | 0.756 | 0.863 | 247.5 / 246.1 / 388.7 |

关键观察：

- **v3 PIPE=2 是唯一真正改变流量等级的配置**：DRAM 从 247 MB 降到 **170.7 MB（−31%）**，L2 命中率从 75.7–80.5% 升到 82.8–84.3%，驻留从 2 CTA/SM 升到 **3 CTA/SM**。TN 因此快 6.7%，NT 持平。
- **v4/v5 PIPE=2 并不减流量**：虽然动态共享内存从 98.4 KB 降到 65.7 KB，但 v4（256 线程 × 109–110 寄存器）与 v5（384 线程 × 58–60 寄存器）的寄存器预算都只能支持 2 CTA/SM，于是只是失去了流水深度，按归一化吞吐计 NT 慢 54–56%、TN 慢 31–32%。
- **PIPE=4 全面失败**：1 CTA/SM、6.2–18.8% occupancy，DRAM 涨到 379–389 MB（+54–58%），L2 命中率降到 61.6–65.3%，所有版本、两个布局都退化。PIPE=4 的深缓冲没有跨 CTA 并发可用，反而降低了 L2 复用。

### 6.4 PIPE 结论

- v3：**NT 长 K 用 PIPE=3，TN 长 K 和 K≤256 用 PIPE=2**；PIPE=4 禁用。
- v4/v5：**保持 PIPE=3**；PIPE=2 在寄存器限制下不能减少驻留 CTA，只会损失流水；PIPE=4 必然掉到 1 CTA/SM。
- 流水深度的收益不是“更深更好”，而是“驻留 CTA 数与 L2 复用”的权衡；PIPE=2 只有配合 v3 的低寄存器/无 producer 结构才能落到 3 CTA/SM。

## 7. M256 线程扫描

### 7.1 NCU 主证据

时长单位 µs，Tensor 为 NCU 报告的 Tensor (FP) 子管线利用率。M128 参考行为同配置的 v4/v5。

| 配置 | 4096³ NT | 4096³ TN | K=256 NT | K=256 TN |
|---|---:|---:|---:|---:|
| v4_m256_t128 | 569.1 / 38.2% | 287.9 / 73.1% | 65.5 / 20.7% | 48.3 / 28.3% |
| v5_m256_t128 | 554.9 / 38.2% | 287.2 / 73.1% | 65.7 / 20.6% | 49.2 / 28.5% |
| v5_m256_t256 | 554.4 / 38.7% | 287.4 / 73.0% | **63.5** / 21.1% | **47.4** / 29.4% |
| v5_m256_t512 | **549.6** / 38.8% | 300.9 / 70.8% | 64.9 / 20.8% | 49.0 / 28.7% |
| M128 v4（参考） | 375.6 / 51.8% | 271.3 / 78.1% | 48.4 / 26.0% | 42.2 / 31.4% |
| M128 v5（参考） | 382.9 / 50.6% | 269.3 / 78.6% | 49.1 / 25.9% | 43.3 / 32.1% |

- M256 在 4096³ 上 **NT 慢 1.44–1.52×，TN 慢 1.06–1.12×**；K=256 上 **NT 慢 1.29–1.35×，TN 慢 1.09–1.15×**。
- M256 的 DRAM 流量与 M128 几乎相同（约 250 MB），但 CTA 数减半，NT 只能取到 **442–453 GB/s**（M128 为 647–659 GB/s），Tensor 利用率 38.2–38.8%（M128 为 50.6–51.8%）。M256 每 CTA 输出翻倍、t128 需要 240 个寄存器/线程，被限制在 1 CTA/SM、2 warp/scheduler，难以隐藏 B 侧取数延迟。
- 增加计算线程到 256/512 只把 NT 从 554.4 改到 549.6 µs（+0.9%），TN 反而从 287.4 改到 300.9 µs（−4.7%）；这再次说明 M256 的瓶颈不是 warp 供给。

### 7.2 官方计时与污染

| 配置 | 4096³ NT | 4096³ TN* | K=256 NT | K=256 TN |
|---|---:|---:|---:|---:|
| v4_m256_t128 | 565.21 | 537.42 | 63.66 | 50.86 |
| v5_m256_t128 | 564.81 | 537.36 | 64.19 | 50.83 |
| v5_m256_t256 | 556.92 | 532.58 | 62.07 | 49.49 |
| v5_m256_t512 | 549.89 | 543.44 | 63.07 | 50.92 |

\* 4096³ TN 的 4 个进程全部受外部进程影响，约为 NCU 的 1.85×，只能组内比较。NT 列的中位数干净（r4 离群被排除），K=256 两列干净。

- NT 长 K：t512 比 t128 快 2.7%，t256 比 t128 快 1.5%；NCU 上对应差异为 0.1–1.0%，方向一致但幅度更小。
- K=256 NT：t256 比 t128 快 3.4%（62.07 vs 64.19 µs）；TN 类似（49.49 vs 50.83，快 2.7%），与 NCU 的 t256 最佳一致。
- TN 长 K：官方受污染，不能用于线程排序；NCU 显示 t128/t256 约 287 µs，t512 约 301 µs。

### 7.3 实现等价性与线程数

- `v4_m256_t128` 与 `v5_m256_t128` 使用同一设备实现和线程组织。官方中位延迟差：4096³ NT 0.07%、TN 0.01%、K256 NT 0.8%、K256 TN 0.06%；NCU 差在时钟差异范围内。**可以视为实现等价**。
- t128/t256/t512 的差异是形状/布局相关的，最大约 5%，没有一致赢家：t256 适合 K=256（两个布局）和 TN 长 K；t512 只在 NT 长 K 上有约 1–3% 优势，却让 TN 长 K 慢 4.7%。

### 7.4 M256 结论

M256 不是 M128 的通用升级，而是一个受形状约束的备选：只有在大 M、需要减少 CTA 数或特定 TN 场景才可能考虑；默认仍用 M128。若使用 M256，**256 个计算线程是更稳的默认值**，512 只用于 NT 长 K 且需逐形状确认。

## 8. NCU 机制分析

### 8.1 4096³ 总表

| 配置 | 布局 | 时长 µs | Tensor % | DRAM GB/s | DRAM MB | L2 命中 % | Occupancy % | CPI |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| v1 | NT | 311.7 | 66.2 | 771.9 | 240.6 | 80.6 | 12.1 | 9.3 |
| v1 | TN | 275.5 | 74.8 | 907.4 | 250.0 | 76.7 | 12.3 | 10.7 |
| v2 | NT | 275.4 | 76.4 | 895.6 | 246.6 | 78.2 | 12.3 | 7.7 |
| v2 | TN | 278.5 | 75.2 | 885.8 | 246.7 | 77.2 | 12.4 | 9.8 |
| v3 | NT | 270.9 | 77.0 | 910.0 | 246.5 | 80.5 | 12.3 | 7.4 |
| v3 | TN | 275.5 | 77.2 | 898.5 | 247.5 | 75.7 | 12.3 | 9.4 |
| v4 | NT | 375.6 | 51.8 | 658.8 | 247.4 | 77.2 | 23.1 | 17.4 |
| v4 | TN | 271.3 | 78.1 | 910.9 | 247.1 | 76.9 | 24.5 | 19.6 |
| v5 | NT | 382.9 | 50.6 | 647.4 | 247.9 | 80.2 | 34.2 | 22.5 |
| v5 | TN | 269.3 | 78.6 | 913.8 | 246.1 | 78.3 | 36.9 | 24.5 |

4096³ 的理论最小 DRAM 流量为 3 × 32 MiB = **100.7 MB**（十进制）。PIPE=3 的所有配置实测 **246–250 MB，约为最小值的 2.45×**；这不是“多读了 1.45 倍”，而是分块后 A/B tile 在 L2 容量（50 MB）内不能完全复用。NT 与 TN 的字节数几乎相同，说明差异不是流量，而是取数效率。

### 8.2 同一份流量，NT 只能取到更低的带宽

最直接的对照是 v4/v5：

| 指标 | v4 NT | v4 TN | v5 NT | v5 TN |
|---|---:|---:|---:|---:|
| 时长 µs | 375.6 | 271.3 | 382.9 | 269.3 |
| DRAM MB | 247.4 | 247.1 | 247.9 | 246.1 |
| DRAM GB/s | **658.8** | **910.9** | **647.4** | **913.8** |
| Tensor % | **51.8** | **78.1** | **50.6** | **78.6** |
| L2 命中 % | 77.2 | 76.9 | 80.2 | 78.3 |
| Occupancy % | 23.1 | 24.5 | 34.2 | 36.9 |
| Eligible warps/scheduler | 0.25 | 0.24 | 0.35 | 0.36 |

两边的 L2 命中率、DRAM 字节数、occupancy 都非常接近，但 NT 的 DRAM 带宽只有 TN 的 0.71–0.72×，Tensor 利用率只有 0.64–0.66×。这不是缓存命中率或总流量能解释的，指向 **NT 的 B 侧取数请求效率/等待链**。v4 NT 的主要 stall 是 L1TEX scoreboard 6.9 cycles + CTA barrier 6.5 cycles（CPI 17.4）；v4 TN 是 barrier 7.5 + L1TEX 7.1（CPI 19.6）。TN 的 CPI 甚至更高，但仍然快，说明“平均 stall 数”不能单独解释，关键在于 stall 期间是否有独立的 Tensor 工作可发射。

### 8.3 更多 warp/occupancy 不能修复 NT

- v3 NT：1.92 active warps/scheduler、12.3% occupancy，却是 NT 最快（270.9 µs、910 GB/s、77.0% Tensor）。
- v5 NT：5.49 warps/scheduler、34.2% occupancy，反而只有 647 GB/s、50.6% Tensor，CPI 22.5，L1TEX stall 12.0 cycles。
- M256 t512 NT：4.98 warps/scheduler、31.1% occupancy，仍有 19.2 cycles L1TEX stall、29.9 CPI，DRAM 只有 453.5 GB/s。

这三组数据说明：**增加 warp 只是增加了更多等待同一取数链的消费者**。一个合理的假设是：v3 的低 occupancy 之所以不吃亏，是因为 compute warp 自己发 TMA、没有 producer/consumer 的额外交接，取数链更短；v4/v5 的专用 producer 增加了 barrier 跳数，在 NT 上无法被额外的 warp 隐藏。该解释仍需 source counters 的 barrier 等待位置来验证。

### 8.4 PIPE 的流量机制

| 配置类 | 驻留 CTA/SM | DRAM MB | L2 命中 % | 4096³ 结果 |
|---|---:|---:|---:|---|
| PIPE=3，M128/M256 | 1–2 | 246–252 | 69.8–80.6 | 基准 |
| v3 PIPE=2 | **3** | **170.7** | **82.8–84.3** | TN 快 6.7%，NT 持平 |
| v4/v5 PIPE=2 | 2（寄存器限制） | 247.4–247.8 | 75.5–76.4 | 慢 31–56% |
| PIPE=4 | 1 | 379.6–388.7 | 61.6–65.3 | 慢 14–95% |

- v3 PIPE=2 的收益来自 **3 个驻留 CTA 带来的跨 CTA L2 复用**：更少 tile 需要从 HBM 重读，流量降 31%，即使用更浅的流水也仍然更快。
- v4/v5 PIPE=2 虽然共享内存更小，但 v4（256 线程 × 109–110 寄存器）和 v5（384 线程 × 58–60 寄存器）仍被寄存器限制在 2 CTA，流量没有下降，只损失了流水深度。
- PIPE=4 的 1 CTA/SM 让同一时刻可复用的邻居 tile 变少，流量反升 54–58%，L2 命中率降到 61.6–65.3%（PIPE=3 为 69.8–80.6%）。这是“深流水”在本实现中的反效果。

### 8.5 K=256 是另一类问题

K=256 只有 4 个 K tile。NCU 的 L2 命中率 93–98%，DRAM 约 26 MB（M128）/ 15 MB（M256，输出写回部分留在 L2），Tensor 利用率 20–32%。这个形状由主循环填充/排空、128×128 输出写回和 CTA 启动主导，不是稳态 DRAM 带宽问题。因此：

- v3 PIPE=2 的 41.0/40.6 µs 是显著且可复现的（官方 40.63/39.75 µs），因为更小的共享内存允许第 3 个 CTA 驻留，帮助隐藏短主循环的固定延迟。
- M256 的 K=256 NT 为 63.5–65.7 µs，比 M128 的 48.4 µs 慢 1.29–1.35×，因为 CTA 数减半后每个 CTA 的输出写回翻倍，固定成本无法摊薄。

### 8.6 机制结论

**有数据直接支持的结论**：

1. 4096³ 的 NT/TN 差异不是 DRAM 总流量（都是约 247 MB），而是可达带宽（659 vs 911 GB/s）和 Tensor 利用率（52% vs 78%）。
2. 增加 occupancy/warp 数不能提高 NT 的取数带宽；v5 的 5.5 warp/scheduler 仍只有 647 GB/s。
3. PIPE 通过驻留 CTA 数改变 L2 复用，进而改变 DRAM 流量；v3 PIPE=2 降 31%，PIPE=4 升 54–58%。
4. M256 的主要损失来自 1 CTA/SM、每 CTA 输出翻倍和 NT 取数效率；线程数只解释 ≤5%。

**仍需补证的假设**：

- NT 的 B 侧 TMA 访问模式（N-major）有更差的请求效率/扇区利用率，导致 L1TEX scoreboard 等待更长；需要 NCU 的 L1 wavefront/sector 指标或 source counters 验证。
- v4/v5 的 producer/consumer barrier 在 NT 上引入了额外的串行跳数；需要用 source counters 定位到具体的 empty/full barrier 等待。
- 16384×1024 与 1024×16384 的 1.1–1.4× 差异来自 CTA 光栅化顺序和 A/B 的 L2 复用差异；需要对这两个形状补 NCU。
- 外部 `./test` 进程占用 HBM 带宽是当前最一致的假设，但日志没有它的负载类型或 per-process 利用率，不能当作已证明的结论。

- 四种输入模式；
- 1/2/3/4/13 个 K tile（覆盖短 K、边界和多次槽位回绕）；
- 每个 C 元素与 CPU CuTe 参考逐一比较，并检查线程到输出的映射。

用例数按配置不同：核心 5 个各 40，PIPE=2 三个各 32，PIPE=4 三个各 48，M256 四个各 40，总计 600。所有正式计时进程的 16 点 precheck/postcheck 也全部 PASS。

这只能证明映射、同步和漏写在小整数输入下正确，**不能替代任意浮点输入、任意 K 和并发 race 的检查**。

## 10. 结论与后续建议

### 10.1 结论

1. **在 H100 PCIe 上，这版自定义 kernel 的稳态上限为 482.4 TFLOPS（63.8% 峰值）**，4096³ NT/TN 都已达到（480.0/482.4）；1024×16384 TN 也能到 473.8。这个水平已经超过同页记录的 cuBLAS 默认路径（409.9），但小形状和短 K 仍有明显差距。
2. **优化步骤的收益顺序是 v2 ＞ v3 ＞ v4/v5**。v2 的双批在途是唯一稳定、大幅的改进；v3 的合并写回基本中性；v4/v5 的 producer/多 warpgroup 只在 1024³/K=256 的 TN 上有效，在 NT 上代价很大。
3. **NT 是当前的主要瓶颈**。在相同流量下，NT 只能取到 TN 的 0.71–0.72× DRAM 带宽和 0.64–0.66× Tensor 利用率；提高 occupancy 不是解药。
4. **PIPE=3 是默认，PIPE=2 是 v3 在 TN 长 K 和短 K 上的专用选择，PIPE=4 应删除**。流水深度通过驻留 CTA 数影响 L2 复用和 DRAM 流量，这一层比“缓冲更深”更重要。
5. **M256 暂不具备替代 M128 的理由**；它的 1 CTA/SM 和翻倍的每 CTA 输出抵消了大 tile 的收益。线程数只带来 ≤5% 的局部差异。

### 10.2 建议的下一步

1. **在独占 GPU 上重跑 PIPE 与 M256 的 4096³**：启动前检查 `nvidia-smi --query-compute-apps`，发现任何外部进程即中止；每组至少 3/4 个进程，保留遥测。当前被污染的绝对值不应写进任何结论。
2. **补做 Compute Sanitizer**：先跑 `v4,v5,v5_m256_t512 × NT,TN × memcheck,racecheck,synccheck`，再考虑扩展到 PIPE 变体。600 个全输出 PASS 不能覆盖 race。
3. **专门攻 NT 取数路径**：用 NCU 的 L1 wavefront/sector、TMA 事务和 source counters 定位 B 侧请求效率；对比 v3（compute 发 TMA）与 v4/v5（producer 发 TMA）的 barrier 等待。可选手段包括 `setmaxnreg`、去掉 NT 的独立 producer、调整 TMA box/swizzle、cluster + TMA multicast、改变 CTA 光栅化。
4. **按形状做版本分派**：NT 大形状用 v2/v3（PIPE=3）；TN 侧只有 1024³（+5.4%）和 K=256（+8.0%）值得用 v4，4096³/16384×1024/1024×16384 的 TN 与 v3 差 ≤1%，维持 v3；v3 的 TN 长 K 用 PIPE=2；1024³ 等小网格优先减少固定开销，不要用 v4/v5 的 NT。
5. **为小形状单独优化**：1024³ 只有 64 个 CTA，v4/v5 NT 的 producer/consumer 串行化会增加约 62% 延迟；可尝试 persistent kernel、合并输出写回、减少 grid 量化，并用 NSYS 检查 CPU 提交空隙。K=256 应重点优化主循环填充/排空和 128×128 写回。
6. **重做 8192³**：延长预热、锁定或至少记录时钟、确保没有外部进程；当前 28 个 warning 和最高 27.7% 的跨度不足以比较版本。
7. **warm full NCU 不再作为必选项**：application replay 的 kernel 集合不一致，修复成本高；如果只需要缓存影响，可在普通计时中改变输入复用策略，或用固定 kernel replay + 明确的缓存控制做对照。
8. **与 cuBLAS 做同布局、同计时的对比**：当前 cuBLAS 记录是 row-major NN、10 次/批、均值；自定义是 NT/TN、20 次/批、中位数。只有统一布局和统计口径，才能把“库 vs 自研”的差距拆成布局、调度和内核本身三部分。
