## 2. 测试口径

- 问题：`C = alpha·A·B + beta·C`，row-major **NN**（transa=N、transb=N），alpha=1、beta=0，输入/输出 FP16，FP32 累加（`FP32_ACC`）。
- cuBLAS 路径：默认启发式 `CUBLAS_GEMM_DEFAULT`，未做 cublasLt 自动调优（`LtCandidates=0`，workspace 由库管理）。row-major NN 在 cuBLAS 列主序视角下对应 TT 路径，不是 cuBLAS 最优布局。
- 计时：`cuda_event_batch_v1`，warmup/repeats/inner = **20 / 50 / 10**；共 50 个样本，每个样本为 10 次连续 launch 的批均耗时；`Time_ms` 为 50 样本均值，`TFLOPS = 2MNK / t`（dense 口径）。
- 缓存条件：`reuse_operands`（操作数跨迭代复用，小形状可能命中 L2），`beta_policy=overwrite`。因此这是 **warm-cache** 结果，不是 cold-HBM 结果。
- 数值校验：每个形状抽样 512 点，atol=5e-4、rtol=1e-3；32/32 PASS，Bad=0；MaxAbsError 9.23e-4–8.05e-3，RelativeL2 1.87e-4–2.22e-4。
- 边界：单次运行、单进程；无运行中频率/功耗遥测（仅启动快照）；同卡有其他进程，不能完全排除干扰；成绩为库调用 + 批内 Event 计时，不是端到端业务耗时。

## 5. 规律分析

### 5.1 大规模形状：400–443 TFLOPS

- 本次最好的是 **M=4096、K=4096 的宽 N 形状**：N=8192 → 442.7，N=16384 → 440.1；N=512/1024 也有 418.9/413.4。
- 方阵在 4096³/8192³ 持续约 **409–410 TFLOPS**（54%）；2048³ 更高（438.1），其工作集 25.2 MB 小于 50 MB L2，且内核时间只有 39 µs，可能受益于缓存与短时 boost，不能直接外推为更大形状也能达到。
- D2/D3/D4 这类 2048 行、K 或 N 加宽的形状为 414–432 TFLOPS，表现稳定。

### 5.2 K 深度与 M 高度

固定 M=N=4096，只改 K：

| K | 128 | 256 | 512 | 1024 | 8192 |
|---|---:|---:|---:|---:|---:|
| TFLOPS | 193.6 | 292.2 | 358.8 | 403.1 | 419.9 |
| 相对 K=8192 | 46% | 70% | 85% | 96% | 100% |

- K=128 时只有约 46% 的饱和吞吐，主循环、流水填充/排空和写回占比过高；K≥1024 后接近平台。
- 固定 N=K=4096，只改 M：1/8/32/128/512/2048 行分别为 **2.6 / 22.7 / 86.6 / 275.8 / 390.3 / 399.8 TFLOPS**。
- M=1 是 GEMV（算术强度≈1）；M=8/32 属于低算术强度、低 SM 占用；M=128 是拐点；M≥512 才进入约 390–400 的平台。
- M=127 与 129 的差异（270.0 vs 246.0）说明 M 落在 tile 边界附近时，网格/tile 量化会带来约 9% 的损失。
- 极瘦长形状 D5/D6（M=32）约 50 TFLOPS：B 矩阵 117.4 MB 需要流式读取，实测等效 HBM 带宽约 **1.69/1.53 TB/s**（约为 2.0 TB/s 规格的 77–85%），属于典型的带宽受限，而不是 Tensor Core 算力问题。

### 5.3 非对齐 N/K：10–12 TFLOPS 的断崖

- F3（N=4095）3.251 ms → 10.6 TFLOPS；F4（K=4095）2.967 ms → 11.6 TFLOPS；两者 50 次样本标准差均不到 0.1%，说明这是**稳定的慢速代码路径**，不是偶发干扰。
- 对照同维度的对齐形状，1024³ 为 227.4 TFLOPS；非对齐形状慢约 **20 倍**。
- 原因假设（尚未用 NCU 证实）：非对齐维度使 `LDA/LDB/LDC = 4095`，FP16 行首地址在 16 B/128 B 边界上错位（8190 B 行距），cuBLAS 很可能退回到不做宽向量化/异步拷贝的 fallback 内核。
- **行动项**：避免 N、K（以及 leading dimension）为奇数；至少补齐到 8 个元素（16 B），追求性能时对齐到 64/128 个元素。当前测试是紧凑打包（ld=N/K），未尝试 padding；补一组 padded 形状即可量化收益。
- M=127/129 没有出现断崖，因为 M 不是行主序的行距，只有 N/K 会影响 stride。

### 5.4 相对峰值的定位

- 442.7 / 756.5 = **58.5%**；大形状常态 53–59%。这已经是本次 cuBLAS 默认启发式在 row-major NN 下的水平，但仍有明显空间。
- 潜在差距来源：row-major NN → 列主序 TT 布局、未启用 cublasLt 自动调优、350 W 功耗上限、长时运行的热/时钟状态，以及本机未锁定频率。
- 不要直接把本结果与同仓库 H800 PCIe 自定义 CUTLASS 的 518 TFLOPS（4096³/TN）比较：GPU 型号、布局、累加精度和计时口径都不同。

## 6. 数据质量与注意事项

1. **D1 的均值不可用**：50 个样本中 49 个为 63.8–76.6 µs，另有一个 2.061 ms 离群点，使均值变为 105.5 µs、TFLOPS 被拉低到 122.2；中位数口径为 65.0 µs / **198.4 TFLOPS**。表中保留均值以便与 `summary.csv` 对齐，但讨论时应使用中位数。
2. **D4/D7 样本分布不平稳**：D4 样本 0.389–0.473 ms、D7 样本 0.294–0.440 ms，呈阶跃、双峰或漂移；对应成绩有约 ±3–6% 的不确定度，建议复测。
3. **小形状均值受离群点影响**：A1 均值 5.85 µs、中位数 4.96 µs；A1/A2 主要反映启动与固定开销，不代表稳定吞吐。
4. **Warm cache**：操作数跨迭代复用；A4、C 系列的 A+B+C 约 25–42 MB，可整体或大部分驻留 L2，因此这些数字相对 cold-HBM 场景偏乐观。
5. **环境条件未完全固定**：同卡存在另一个 472 MiB 进程；运行过程中没有遥测；功耗上限 350 W，未锁频；不同时间段的 boost/温度可能影响长形状。
6. **布局与调优**：row-major NN + 默认启发式 + 无 cublasLt 调优，不能代表 cuBLAS 在该 GPU 上的最优配置，也不能直接作为 CUTLASS 内核的“库上限”基线。

## 7. 结论与后续建议

**结论**

- 在 H100 PCIe 上，cuBLAS FP16（FP32 累加）默认路径处理 row-major NN GEMM：大且对齐的形状可达 **400–443 TFLOPS（53–59%）**；4096³/8192³ 的持续水平约 **410 TFLOPS**。
- 性能主要受四类因素支配：固定开销（<10 µs）、K 深度、M 高度/并行度与带宽、以及 N/K 的对齐。非对齐 N/K 的损失可达 20 倍，优先级最高。
- 小形状（M≤32）与 K≤512 的形状不适合用“峰值占比”评价，应按延迟/带宽模型单独看。

**建议的下一步**

1. 用 padded 形状（如 4096×4096×4096 对比 4095 版本）验证对齐假设，并给出 padding 的收益曲线。
2. 同一 shape 补测 NT/TN 布局与 cublasLt 调优，区分“布局损失”和“库默认启发式损失”。
3. 对 E3、A5、F3、F4 做 NCU 采集，确认 Tensor 利用率、DRAM/L2 流量和 fallback 内核形态，把“假设”变成证据。
4. 复测 D1、D4、D7（以及 A1 的固定开销），确认离群点来源；有条件时独占 GPU、锁频并同步记录功耗/时钟。
5. 将本次 cuBLAS 结果与同 shape、同布局、同累加精度、同计时口径的 CUTLASS 结果并列，作为“库 vs 自研”的可比基线。
