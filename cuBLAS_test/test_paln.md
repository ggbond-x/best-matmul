我设计了一套 24 组核心 GEMM Shape + 8 组扩展 Shape，用于对比 cuBLAS、DeepGEMM 和你自己实现的 CUDA GEMM 算子。

这套测试主要面向 NVIDIA H100（Hopper）架构，重点不是简单地罗列矩阵大小，而是通过不同形状的矩阵，系统性地评估：

1. 峰值计算性能：大矩阵下能达到多少 TFLOPS。
2. 不同矩阵形状的适应性：Square、Tall-Skinny、Short-Wide 等场景。
3. 大模型推理性能：Prefill 和 Decode 阶段常见的 GEMM。
4. 算子优化能力：Tile 利用率、SM 并行度、Pipeline 效率、访存效率。

## 一、首先统一测试规范

矩阵乘定义为：
$$
C_{M\times N}=A_{M\times K}\times B_{K\times N}
$$
对应计算量：
$$
FLOPs=2MNK
$$
性能计算公式：
$$
TFLOPS=\frac{2MNK}{T_{\text{ms}}\times10^9}
$$
其中 \(T_{\text{ms}}\) 是 GPU 执行耗时，单位为毫秒。

一个重要前提：三套实现必须使用相同的数据类型、矩阵布局和计算语义。

根据当前 DeepGEMM 官方源码，它支持 BF16 和 FP8 等 GEMM，但不能直接假设它与 FP16 cuBLAS GEMM 使用相同的计算路径。特别是部分 BF16 调用可能内部转发到 cuBLASLt，因此还要检查实际调用的 kernel，避免出现两个看似不同的库实际上执行相同后端的情况。

建议分成两条测试线：

- BF16 三方对比：cuBLAS / DeepGEMM / 自研 BF16 GEMM。
- FP16 专项对比：cuBLAS / 自研 FP16 WGMMA GEMM。

后续如果三方都实现 FP8，再增加独立的 FP8 对比，不能把 FP8 与 FP16 的 TFLOPS 直接当作同精度算法的优劣结论。

## 二、24 组核心测试 Shape

### A 组：Square GEMM（6 组）

目标：测试矩阵乘算子的计算吞吐能力，以及矩阵规模增大时的性能变化。

| ID   | M    | N    | K    | 测试目的     |
| ---- | ---- | ---- | ---- | ------------ |
| A1   | 256  | 256  | 256  | 小矩阵       |
| A2   | 512  | 512  | 512  | 较小规模     |
| A3   | 1024 | 1024 | 1024 | 中等规模     |
| A4   | 2048 | 2048 | 2048 | 大矩阵       |
| A5   | 4096 | 4096 | 4096 | 峰值性能重点 |
| A6   | 8192 | 8192 | 8192 | 超大矩阵吞吐 |

这组主要分析 GEMM 随着矩阵规模增长的性能变化。

Square GEMM 理论计算量

仅表示计算规模，不是实际测试性能


重点观察 A4、A5、A6 是否能够达到稳定的高吞吐率，以及是否存在大矩阵性能下降的问题。

### B 组：K 维度变化（5 组）

目标：研究 K 维度对 WGMMA、TMA Pipeline 和计算访存重叠效率的影响。

固定 M=N=4096。

| ID   | M    | N    | K    | 测试目的       |
| ---- | ---- | ---- | ---- | -------------- |
| B1   | 4096 | 4096 | 128  | 很浅的 K 维度  |
| B2   | 4096 | 4096 | 256  | 少量 K Tile    |
| B3   | 4096 | 4096 | 512  | 中短 K         |
| B4   | 4096 | 4096 | 1024 | 中等 K         |
| B5   | 4096 | 4096 | 8192 | 深 K，长流水线 |

这组与你目前的 Hopper WGMMA + TMA GEMM 优化关系尤其密切。

例如，对于 `BLK_K=64`：
$$
K_{\mathrm{tiles}}=\left\lceil\frac{K}{64}\right\rceil
$$
当 K=128 时只需要 2 个 K Tile，而 K=8192 时需要 128 个 K Tile。

你可以研究 Pipeline Stages=2/3/4 对性能的影响，以及短 K 场景中 Pipeline 启动和收尾开销是否占比较高。

### C 组：M 维度变化（6 组）

目标：测试不同并行规模下，SM 利用率和 Tile 利用率的变化。

固定 N=K=4096。

| ID   | M    | N    | K    | 测试目的             |
| ---- | ---- | ---- | ---- | -------------------- |
| C1   | 1    | 4096 | 4096 | 单 Token / GEMV-like |
| C2   | 8    | 4096 | 4096 | 极小 Batch           |
| C3   | 32   | 4096 | 4096 | 小 Batch             |
| C4   | 128  | 4096 | 4096 | 中小 Batch           |
| C5   | 512  | 4096 | 4096 | 中等 Batch           |
| C6   | 2048 | 4096 | 4096 | 大 Batch             |

当 M=1 时，如果仍然使用 `BLK_M=128`，一个 M Tile 只有一行有效数据。

这组能够帮助你判断是否有必要针对小 M 设计专用 kernel，或针对 GEMV-like 场景采用不同的计算实现。

### D 组：LLM 推理常见形状（7 组）

目标：测试更贴近实际模型推理负载的 GEMM。

以下以 Hidden Size=4096 的模型结构作为代表，采用不同中间维度构造算子测试。

| ID   | M    | N     | K     | 对应场景                  |
| ---- | ---- | ----- | ----- | ------------------------- |
| D1   | 128  | 12288 | 4096  | 小 Prefill，融合 QKV 投影 |
| D2   | 2048 | 12288 | 4096  | Prefill，融合 QKV 投影    |
| D3   | 2048 | 11008 | 4096  | FFN Up Projection         |
| D4   | 2048 | 4096  | 11008 | FFN Down Projection       |
| D5   | 32   | 14336 | 4096  | Decode，MLP Up            |
| D6   | 32   | 4096  | 14336 | Decode，MLP Down          |
| D7   | 512  | 32000 | 4096  | LM Head / Logits          |

这里的 M 可以理解为参与本次矩阵乘的 Token 总数，而不一定等于请求数量。

例如在 D3：
$$
[2048,4096]\times[4096,11008]
$$
对应 Transformer FFN 中的一个 Up Projection 计算。

需要注意，D1/D2 是完整 QKV 投影的示意形状，实际使用 GQA 的模型，其 QKV 输出维度不一定是 `3×hidden_size`。

## 三、8 组扩展 Shape

核心 24 组用于初步衡量性能，扩展组用于进一步定位性能瓶颈。

### E 组：N 维度变化（4 组）

固定 M=K=4096。

| ID   | M    | N     | K    |
| ---- | ---- | ----- | ---- |
| E1   | 4096 | 512   | 4096 |
| E2   | 4096 | 1024  | 4096 |
| E3   | 4096 | 8192  | 4096 |
| E4   | 4096 | 16384 | 4096 |

用于研究 N 方向的 CTA 划分、并行度和矩阵输出规模对性能的影响。

### F 组：非对齐 Shape（4 组）

| ID   | M    | N    | K    | 测试目的           |
| ---- | ---- | ---- | ---- | ------------------ |
| F1   | 127  | 4096 | 4096 | M 未对齐 128       |
| F2   | 129  | 4096 | 4096 | 跨越一个 Tile 边界 |
| F3   | 1024 | 4095 | 4096 | N 尾块             |
| F4   | 1024 | 4096 | 4095 | K 尾块             |

该组主要用于检查边界处理、Padding 和无效计算开销。部分 DeepGEMM kernel 对 Shape 或内存对齐有约束，不支持的形状应标记 `Unsupported`，不要强行将其计入三方平均加速比。

## 四、建议的性能结果表格

我建议你的最终测试数据至少包含以下字段。

| Shape ID | M×N×K          | cuBLAS (TFLOPS) | DeepGEMM (TFLOPS) | 自研 (TFLOPS) |
| -------- | -------------- | --------------- | ----------------- | ------------- |
| A1       | 256×256×256    | —               | —                 | —             |
| A2       | 512×512×512    | —               | —                 | —             |
| A3       | 1024×1024×1024 | —               | —                 | —             |
| A4       | 2048×2048×2048 | —               | —                 | —             |
| A5       | 4096×4096×4096 | —               | —                 | —             |
| A6       | 8192×8192×8192 | —               | —                 | —             |

同时建议记录三套 kernel 的执行延迟（μs），并计算自研算子相对 cuBLAS 的加速比：
$$
Speedup=\frac{T_{\mathrm{cuBLAS}}}{T_{\mathrm{Custom}}}
$$
除了 TFLOPS，你还需要保留运行数据类型、Tensor Layout、实际 kernel 名称、正确性测试结果、GPU 型号、CUDA 版本等元数据。

测试时应将 JIT 编译、初始化及显存分配排除在纯 kernel 延迟测量之外，使用 GPU Event、预热和重复测试。NVIDIA CUTLASS 的性能测量指南还特别强调对 GPU 缓存状态和输入 buffer 轮换的控制。

对于 M=1、8、32 这样的场景，要同时关注延迟，因为低 TFLOPS 可能只是问题规模太小，而不一定说明实际推理性能差。
